A user sends one prompt:

> Read the project materials, compare three implementation options, and produce a Markdown report with sources.

The nine stops follow this request through reading, optional delegation, and report delivery. **The model chooses actions; the runtime supplies capabilities, constrains execution, and records results.** The chapters introduce concepts in reading order. During execution, skills participate in assembly, sandbox creation can be deferred, and delegation happens when needed.

First, we follow the text into a thread, a run, and an observable event stream.

## From the composer to HTTP

Frontend <SourceRef file="frontend/src/core/threads/hooks.ts" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> uses the LangGraph SDK's `useStream`. The send handler uploads attachments, then calls `thread.submit()`: `messages` carries text and attachment information, `context` carries runtime preferences, and `threadId` identifies the conversation.

This path enables `streamResumable` without `streamSubgraphs`. Delegated progress arrives through root-namespace custom events; a subgraph's complete `values` must not overwrite root conversation state.

The deployment proxy forwards `/api/langgraph/*` to Gateway's compatible routes. Using the SDK protocol **does not require an official LangGraph Server behind it**.

| Object | Responsibility |
| --- | --- |
| thread | A conversation across turns |
| run | One managed execution on that thread |
| LangGraph | Graph execution and state updates |
| Gateway | Admission, permissions, runs, streams, persistence, finalization |
| LangGraph Server | An optional host, not an intermediary on this Web path |

## Gateway starts with admission

<SourceRef file="backend/app/gateway/routers/thread_runs.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="stream_run" /> checks creation permissions and thread ownership, then calls <SourceRef file="backend/app/gateway/services.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="start_run" />. Before launching execution, it:

1. Normalizes messages and strips forged server metadata and internal context keys.
2. Injects authenticated identity, validates model selection, and bounds recursion.
3. Pins project scope and prepares read-only access to referenced conversations.
4. Prepares input, config, and record data for `RunManager.create_or_reject()`.
5. Launches execution after creation. Idempotent reuse must not execute the request twice.

For our prompt, the server-owned project snapshot answers “which materials?” It prevents one run from resolving project relationships differently at every step.

<MarginNote>A checkpoint is the state snapshot LangGraph saves after each graph step. Resuming a conversation later depends on it. In the next section's table, “data updated and checkpointed by the graph” means exactly that saved part.</MarginNote>

<MarginNote>Writing “I am an administrator” supplies text, not authority. Access to threads, models, and tools comes from authentication and authorization.</MarginNote>

## One execution chain, three waiting modes

Background creation returns a record immediately; `/runs/stream` returns SSE (Server-Sent Events, a one-way event stream from the server); `/runs/wait` waits for completion. They share admission and lifecycle logic.

The bridge separates production from HTTP consumption. `on_disconnect=continue` permits execution to continue; `cancel` requests cancellation through ownership and finalization rules. Joining an existing stream observes a run without creating another or automatically inheriting the creator's disconnect policy.

`Content-Location` identifies the canonical run resource. An in-memory bridge is process-local: a durable record from another worker does not imply an available local stream. The route rejects this unsupported subscription instead of waiting on an empty log.

## A lifecycle exists before reasoning

<SourceRef file="backend/packages/harness/deerflow/runtime/runs/manager.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="RunManager" /> handles admission, state, ownership, and cancellation. <SourceRef file="backend/packages/harness/deerflow/runtime/runs/worker.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="run_agent" /> invokes the graph, publishes events, and finalizes. Neither is the model.

With heartbeat enabled, remote cancellation can persist an intent for the owner to observe. Expired-run recovery must also check ownership. Single-process mode has different boundaries, covered at stop nine.

<Philosophy>
Gateway turns model interaction into manageable application execution. The cost is maintaining boundaries between the SDK protocol, graph state, and business records. Identify who accepts, owns, observes, and terminates the request.
</Philosophy>
