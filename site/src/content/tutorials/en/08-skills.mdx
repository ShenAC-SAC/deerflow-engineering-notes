A skill can specify how to select sources, format citations, and check a report. It packages a workflow, references, and scripts for on-demand reading.

**Skills package working methods; the agent's configuration, authorization, and runtime policy determine which capabilities those methods can use.**

## Packages, metadata, and ownership

<SourceRef file="backend/packages/harness/deerflow/skills/types.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="Skill" /> records name, description, location, category, enabled state, compatibility fields, and secret requirements. <SourceRef file="backend/packages/harness/deerflow/skills/parser.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> parses frontmatter and discovers packages. A directory containing SKILL.md is a package boundary, not a reason to register every nested file as another top-level skill.

Public skills are shared. <SourceRef file="backend/packages/harness/deerflow/skills/storage/user_scoped_skill_storage.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="UserScopedSkillStorage" /> scopes custom skills to a user while retaining shared public reads. Integration packages join through their registry and projection mechanisms, contributing another source of discoverable skills.

A hypothetical report skill might contain:

~~~text
report-sources/
  SKILL.md
  references/citation-guide.md
  scripts/check_links.py
~~~

SKILL.md describes the workflow, references supplies supporting material, and scripts holds helper programs. Execution requires the appropriate tools, environment, and authorization.

## Two discovery modes

When `skills.deferred_discovery` is disabled, prompts list skill metadata. When enabled, a compact index and <SourceRef file="backend/packages/harness/deerflow/skills/describe.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="build_describe_skill_tool" /> provide progressive discovery.

`describe_skill` returns metadata and paths; the model then decides whether to read SKILL.md. It does not promote tool schemas like MCP `tool_search`, and the two deferred switches are independent.

Explicit `/skill` activation uses <SourceRef file="backend/packages/harness/deerflow/agents/middlewares/skill_activation_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="SkillActivationMiddleware" /> for deterministic loading, still constrained by available skills and activation authorization.

## Visibility, activation, and execution differ

| Boundary | Mechanism |
| --- | --- |
| Listed as a candidate | Agent scope and resource authorization |
| Described or activated | Action authorization such as `skill:activate` |
| Readable in the sandbox | Provider support and managed projection |
| Tool invocation permitted | Agent configuration, tool authorization, runtime policy |

<SourceRef file="backend/packages/harness/deerflow/authz/skill_filter.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> handles skill authorization. A custom provider can permit visibility but deny activation.

The parser and Skill retain `allowed-tools` for compatibility and metadata exchange. A non-empty field does not narrow tool permissions; activation does not expand them.

## Filesystem projection controls actual visibility

<SourceRef file="backend/packages/harness/deerflow/skills/projection.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> builds managed enabled/permitted views for `/mnt/skills`. Restricted thread views use copies, validate paths and links, and maintain stable mount roots and freshness signatures.

Copying and signing content costs I/O and storage while separating sandbox edits from canonical skill files. Policy changes must revoke the old scope rather than merely append new packages.

Not every provider supports this boundary. Unsupported physical isolation requires explicit handling. Children sharing a sandbox must not rebuild its lead-owned skill projection.

## Installation has a publication boundary

<SourceRef file="backend/packages/harness/deerflow/skills/installer.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="safe_extract_skill_archive" /> unconditionally checks archive paths, entry counts, expanded size, and executable binaries. When scanning is enabled, native <SourceRef file="backend/packages/harness/deerflow/skills/skillscan/orchestrator.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> and content scanning inspect package text/scripts before publication.

Passing a scanner does not prove runtime safety or the absence of misleading instructions. Static checks, model review, authorization, and isolation have distinct responsibilities.

<SourceRef file="backend/packages/harness/deerflow/tools/skill_manage_tool.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> constrains agent writes to managed operations. Extensions can also use <SourceRef file="backend/packages/harness/deerflow/skills/mutations/service.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="HostSkillMutationService" />, whose staging, checking, revision validation, and publication separate proposed text from an installed change.

## Secrets are runtime capabilities

Skills may declare required secrets; binding also depends on activation and policy. Values belong in runtime capability channels, not SKILL.md, conversation, checkpoints, or shareable artifacts. Naming a credential requirement does not grant access to it.

<Philosophy>
Progressive loading controls context cost. Resource authorization and physical projection govern real access. Keeping those separate avoids treating omission from a prompt as access control.
</Philosophy>

For our report, the skill supplies methods while authorization and filesystem views constrain access. Next, we inspect execution records and restart behavior.
