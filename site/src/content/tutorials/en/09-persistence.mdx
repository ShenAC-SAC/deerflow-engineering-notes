After the report is generated, the user closes the page or restarts Gateway. What should remain? **A database alone does not answer this: graph state, conversations, runs, events, and files have different owners.**

Recovering state neither restores a live Python task nor reverses external requests and file writes.

## Startup assembles infrastructure

<SourceRef file="backend/app/gateway/deps.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="langgraph_runtime" /> uses a startup snapshot for the engine, checkpointer, Store, run/event/thread stores, bridge, and RunManager. These connection-owning instances bind to startup configuration; switching backends requires restart.

Requests can read hot-reloadable settings, but existing stores must remain paired with their startup configuration. Otherwise configuration can describe Redis while the process still uses a memory object.

## Six persistence surfaces

| Surface | Stores | Does not replace |
| --- | --- | --- |
| Checkpointer | Graph channels and resume positions | Undo for external side effects |
| LangGraph Store | Namespaced long-term data | A live task |
| RunStore | Status, owner, lease, cancellation, completion | Complete graph state |
| RunEventStore / Journal | Messages, tool and lifecycle events | Proof of business correctness |
| ThreadMeta | List/title/owner information | The entire conversation |
| Files and blobs | Uploads, reports, large outputs | Availability inferred solely from database rows |

<SourceRef file="backend/packages/harness/deerflow/runtime/journal.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="RunJournal" /> turns callbacks and messages into queryable events. Graph checkpoints, event persistence, and run finalization can complete at different times. Success on one surface does not establish that all others committed.

## Database and checkpointer configuration precedence

<SourceRef file="backend/packages/harness/deerflow/config/database_config.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="DatabaseConfig" /> supplies the unified database settings. Checkpointer and Store factories give an explicit `checkpointer` section precedence, then fall back to `database` when it is absent.

Resolve the effective backend using this precedence, then check its durability. Memory, SQLite, Postgres, and file storage have different restart behavior.

## Schema migration differs from checkpoint representation

<SourceRef file="backend/packages/harness/deerflow/persistence/bootstrap.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> owns application schema initialization:

- Empty databases create current tables and stamp migration head.
- Databases with application tables but no Alembic revision backfill baseline tables and apply subsequent revisions.
- Versioned databases use Alembic (SQLAlchemy's migration tool) upgrades.
- Unknown/incompatible revisions are rejected, with explicitly reviewed forward-compatibility windows rather than arbitrary acceptance.

This differs from `full / delta` graph-state representation. Optional delta mode changes accumulating-channel persistence. Shared processes need compatible modes and changes require restart.

<SourceRef file="backend/packages/harness/deerflow/runtime/checkpointer/cached_saver.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="CachedHistorySaver" /> caches delta histories addressed by immutable checkpoint IDs, not an indefinitely cached “latest checkpoint.” The cache is not authoritative; deletion and pruning must account for it.

## Runs have worker ownership and heartbeat

With heartbeat enabled, <SourceRef file="backend/packages/harness/deerflow/runtime/runs/manager.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="RunManager" /> uses durable ownership and leases for status writes, cancellation, and orphan recovery.

| Situation | Boundary |
| --- | --- |
| Local active owner | Cancel locally and finalize |
| Another owner's lease is valid | Persist cancellation intent for its heartbeat to observe |
| Lease expired | Conditionally reclaim and mark error, not transparently resume the original Python execution |
| Single-process store-only hydration | No local task is available to cancel; return a conflict |
| Old owner lost its lease | Reject stale finalization |

Leases constrain ownership of run records. A third-party request sent before ownership was lost can still have effects, so external operations need their own idempotency contract.

## Cancellation, rollback, and recovery promises

Interrupt can retain checkpoints; rollback can restore supported pre-run graph state. Neither automatically reverses report writes, sent messages, or external database mutations.

For our report, check separately:

1. Whether the run completed or stopped.
2. Whether the conversation can continue from its checkpoint.
3. Whether messages and events remain queryable.
4. Whether the report still exists and is readable under authorization.
5. Whether retrying duplicates external effects.

<Philosophy>
Useful persistence contracts state what each surface can recover. Database rows, live streams, and external files have different lifetimes. Treating them as one promise of recoverability hides the failures that matter most.
</Philosophy>
