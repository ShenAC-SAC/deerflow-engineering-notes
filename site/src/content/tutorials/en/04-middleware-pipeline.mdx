With the model and tools selected, middleware prepares the input: conversation history, project scope, uploaded files, and the current date. Long conversations may also need compaction. Throughout these transformations, tool calls and results must retain their message protocol.

**Identify a middleware's hook and state ownership before interpreting its position in the list.** One object can participate at both model and tool boundaries.

## Interpret order per hook

~~~text
Registration: A, B, C

before_*: A → B → C
after_*:  C → B → A
wrap_*:   A wraps B, B wraps C; results unwind outward
~~~

Not every middleware implements every hook. Tool wrappers surround actual tool execution; they are not ordinary reverse-order `after_model` callbacks.

<SourceRef file="backend/packages/harness/deerflow/extensions/ordering.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="assert_ordering" /> validates declared ordering constraints after extension composition. Dependencies outside those constraints require inspection of hook implementations and behavioral tests.

## before_agent: prepare paths and execution resources

ThreadData prepares thread paths, Uploads supplies attachment context, and Sandbox manages execution resources. Lazy initialization usually defers creation until use; restricted skill projection and enabled prewarming can acquire an environment earlier.

An uploaded file still needs a usable virtual path and context for the model. Project materials may be exposed as an index with on-demand retrieval rather than inserted wholesale.

## before_model: extract continuity from messages

<SourceRef file="backend/packages/harness/deerflow/agents/middlewares/durable_context_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="DurableContextMiddleware" /> captures delegation and loaded-skill information into separate state channels. <SourceRef file="backend/packages/harness/deerflow/agents/thread_state.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="ThreadState" /> also carries `summary_text`, `tool_artifacts`, and `task_notes`.

These preserve useful continuity without relying exclusively on an ever-growing transcript. Delegation identity includes run context: repeated provider tool-call IDs across runs must not identify the same execution.

When enabled and triggered, <SourceRef file="backend/packages/harness/deerflow/agents/middlewares/summarization_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> compacts history while retaining recent context and protocol boundaries. Compaction does not turn evidence into verified conclusions. Summaries, task notes, and child reports remain fallible; source recovery can be necessary.

## wrap_model_call: produce a request view

| Operation | Persistent graph-state effect |
| --- | --- |
| Return a state update, merged through reducers | Updates graph state; durability depends on checkpointing |
| `request.override(messages=...)` | Changes this model request without automatically rewriting checkpoints |

<SourceRef file="backend/packages/harness/deerflow/agents/middlewares/dynamic_context_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> provides changing date and memory context while keeping the base system prompt stable where possible. DurableContext temporarily adds an authority contract and hidden data message containing summaries, delegations, skills, artifacts, and enabled task-continuity data.

Runtime-provided history does not gain system authority. An active goal carries the user's objective at user-request authority; other historical fields remain data.

## Message transformations must preserve provider contracts

<SourceRef file="backend/packages/harness/deerflow/agents/middlewares/dangling_tool_call_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> repairs dangling tool calls. Sanitization, compaction, fallbacks, and history trimming must collectively preserve call/result pairing.

SystemMessageCoalescing combines system content at the request boundary; ModelContentCompatibility adapts particular content forms. These concern the provider request, not necessarily the visible conversation history.

<Philosophy>
Separating durable state from temporary request views allows recovery, context budgeting, and provider compatibility to coexist. The useful question is ownership: what must be recorded, and what should appear only in this model call?
</Philosophy>

With input prepared, the model can answer or propose tool calls. Next, we follow response checks, tool execution, and finalization.
