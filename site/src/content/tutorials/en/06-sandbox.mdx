Suppose the model decides to read project files and write the report. Tool schemas describe the call; the sandbox answers **where it executes, who owns the files, and what happens to resources afterward**.

Sandbox provides a common operations interface; isolation depends on the execution environment. Local execution, containers, and remote services require separate checks for paths, commands, networking, and operating-system isolation.

## Conversation identity, resource handles, and ownership

`thread_id` identifies a conversation; `sandbox_id` is a resource handle. <SourceRef file="backend/packages/harness/deerflow/sandbox/sandbox_provider.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="SandboxProvider.get_scoped" /> checks thread/user scope. Its default cannot establish ownership, so it returns no resource and callers use canonical acquisition.

A checkpoint can survive when its original process, container, or client does not. A recorded name cannot replace checking the live resource.

## Stable virtual paths, different physical locations

The model commonly sees `/mnt/user-data/workspace`, `uploads`, and `outputs`. Local mapping, container mounts, and remote upload/download can implement those paths differently.

Writing a virtual report path does not establish that the same absolute path exists on the host. <SourceRef file="backend/packages/harness/deerflow/sandbox/tools.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> connects calls to the sandbox and result metadata; delivery requires the relevant file service too.

`/mnt/skills` is a managed view. <SourceRef file="backend/packages/harness/deerflow/skills/projection.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> projects enabled and permitted packages instead of blindly exposing the full library.

## Lazy acquisition and shared leases

Default lazy acquisition can avoid remote-environment creation for text-only work when no restricted skill projection or prewarming requires it. A policy-scoped projection can acquire in before_agent to synchronize files; enabled prewarming can also prepare resources earlier. Once used, lead and child executions hold separate execution leases.

If a lead finishes while a child still reads a file, releasing the lead's lease must not remove the child's environment. Only the final borrower triggers provider release, which can park a remote resource in a warm pool.

**These are process-local resource leases.** They differ from RunManager's worker-ownership leases and do not alone establish cross-process coordination. AIO ownership and E2B capacity have their own mechanisms.

## Skill views have an owner too

The lead can build a thread projection for its agent policy. Children share that sandbox and must not rebuild the mount according to their own skill lists, changing files for concurrent users of the environment.

`supports_agent_skill_isolation` describes whether a provider can enforce this physical boundary. Unsupported isolation must not silently degrade into hiding names in the prompt.

## Cleanup during cancellation

Normal `after_agent` releases the claim. Errors and cancellation also require cooperation among workers, tools, and lifecycle helpers. A synchronous provider operation may continue in a worker thread after its caller is cancelled; cleanup must not remove its resources prematurely.

<Philosophy>
Sandbox lifecycle is first an ownership question. Preserving thread data, retaining a warm environment, and releasing one execution's claim are distinct operations. Keeping them separate prevents one completed chat action from disrupting another active execution.
</Philosophy>
