报告生成后，用户关闭页面，甚至重启 Gateway，再回来应该看到什么？**“存了数据库”不是完整答案：对话、图状态、run、事件和文件由不同机制保存。**

而且恢复状态不等于恢复仍在执行的 Python task，更不等于撤回已经发送的网络请求或写入的外部文件。

## 启动时装配的是一组运行基础设施

<SourceRef file="backend/app/gateway/deps.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="langgraph_runtime" /> 使用启动配置快照创建 engine、checkpointer、Store、run/event/thread 存储与 StreamBridge，并构造 RunManager。这些连接与存储实例绑定启动配置，切换后端需要重启。

启动后请求可以读取允许热更新的配置，但 event store 等仍须与当初实例使用的配置配对。否则会出现“新配置描述 Redis，进程却仍在用内存对象”的错位。

## 先把六类数据分开

| 数据面 | 记录什么 | 不能代替什么 |
| --- | --- | --- |
| Checkpointer | 图状态、channel 和恢复位置 | 外部副作用的撤销记录 |
| LangGraph Store | namespace/key 形式的长期数据 | 一个仍活着的执行 task |
| RunStore | 状态、归属、租约、取消和完成数据 | 完整图状态 |
| RunEventStore / Journal | 消息、工具及生命周期事件 | 业务结论正确性的证明 |
| ThreadMeta | 列表、标题、属主等会话外壳 | 全部对话内容 |
| 文件与 blob | 上传、报告和大工具输出 | 数据库记录存在就能推定的文件可用性 |

<SourceRef file="backend/packages/harness/deerflow/runtime/journal.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="RunJournal" /> 将回调和运行消息转成可查询事件。事件流、图 checkpoint 与 run 状态可能在不同时间完成写入；不能从某一层成功推断所有层已经提交。

## database 与 checkpointer 的配置优先级

<SourceRef file="backend/packages/harness/deerflow/config/database_config.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="DatabaseConfig" /> 是统一数据库配置入口。<SourceRef file="backend/packages/harness/deerflow/runtime/checkpointer/async_provider.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 所示的 checkpointer 工厂与 Store 工厂优先使用显式 `checkpointer` 配置；未配置时跟随 `database`。

判断数据能否跨重启保留，需要先按这一优先级解析出实际后端，再分别检查 memory、SQLite、Postgres 和文件存储的持久化条件。

## schema migration 与 checkpoint 表示不同

<SourceRef file="backend/packages/harness/deerflow/persistence/bootstrap.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 管理应用表 schema：

- 空库建立当前表结构并标记 migration head。
- 存在应用表但没有 Alembic 版本记录的数据库，先补齐 baseline 表，再执行后续 revision。
- 已版本化数据库按 Alembic 升级。
- 对未知或不兼容的 migration revision 拒绝启动；经过明确审查的前向兼容窗口按专门规则处理。

这与图状态的 `full / delta` 表示是不同问题。默认的 full 与可选 delta 决定累积 channel 怎样保存；共享数据库的进程必须使用兼容模式，修改需重启。

<SourceRef file="backend/packages/harness/deerflow/runtime/checkpointer/cached_saver.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="CachedHistorySaver" /> 缓存按明确 checkpoint ID 定位的 delta history，而不是把“最新 checkpoint”永久缓存。缓存不是真相源；线程删除或历史清理也要处理相关缓存。

## Run 的 worker 所有权与心跳

<SourceRef file="backend/packages/harness/deerflow/runtime/runs/manager.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="RunManager" /> 管理执行的归属。启用 heartbeat 后，持久化的属主与租约参与状态写入、取消和失联 run 的回收。

| 场景 | 行为边界 |
| --- | --- |
| 当前 worker 拥有活跃执行 | 请求本地取消，并走终态收尾 |
| 另一个 worker 的 lease 有效 | 持久化取消意图，由属主心跳观察并执行 |
| lease 过期 | 经条件检查回收并标记错误，不接续已经退出的 Python 执行 |
| 单进程模式下仅恢复出 store-only 记录 | 没有可取消的本地 task，按冲突返回 |
| 旧 owner 已失去归属 | 不能继续用旧执行写入最终状态 |

租约约束的是运行记录的所有权。进程失去归属前发出的第三方请求仍可能产生副作用，因此外部操作需要独立的幂等协议。

## Redis bridge 与部署门槛

<SourceRef file="backend/packages/harness/deerflow/runtime/stream_bridge/redis.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 实现 Redis stream，支持跨进程订阅、事件 ID、有限重放和生产者生命周期管理。它的缓存期限与缺口处理意味着：重连不是无限历史数据库。

<SourceRef file="backend/packages/harness/deerflow/config/deployment_config.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 与 Gateway 启动校验要求多进程拓扑使用匹配的共享数据库、run heartbeat 和 Redis bridge，并对 scheduler、sandbox ownership、进程内 browser 等额外能力检查兼容性。**换成 Postgres 并不足以自动获得完整多实例支持。**

## cancel、rollback、恢复分别承诺什么

`interrupt` 可以保留 checkpoint；`rollback` 可以恢复受支持的运行前图状态。两者都不能自动撤销报告写入、邮件发送、外部数据库更新等副作用。

对于示例报告，应分别核对：

1. run 是否已完成或中断；
2. checkpoint 能否继续对话；
3. 事件与消息是否可查询；
4. 报告文件是否仍存在、可授权读取；
5. 若重试生成，是否会重复影响外部系统。

<Philosophy>
持久化的工程价值是明确每一层能恢复什么。数据库记录、实时流和外部文件有不同生命周期；将它们说成一个“可恢复”承诺，反而掩盖最需要检查的失败边界。
</Philosophy>
