模型和工具选好后，middleware 负责准备模型输入。对于报告请求，这包括消息历史、项目资料范围、上传文件和当前时间；对话较长时还需要压缩上下文。处理这些内容的同时，middleware 也维护工具调用与结果的消息协议。

**读 middleware 时，先问它挂在哪个 hook、读写哪种状态，再问它在列表中的位置。** 同一个对象可能同时参与模型调用和工具执行。

## 共享基座与 lead 专属层

<SourceRef file="backend/packages/harness/deerflow/agents/middlewares/tool_error_handling_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="build_lead_runtime_middlewares" /> 提供共享运行基座，<SourceRef file="backend/packages/harness/deerflow/agents/lead_agent/agent.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="build_middlewares" /> 再增加 lead 专属处理，最后合并 extension 贡献。

阅读时可以先按职责分组。下表是**职责索引，不是可以直接拿去重排的完整执行顺序**：

| 处理组 | 代表机制 | 本次请求需要它解决什么 |
| --- | --- | --- |
| 不可信输入 | InputSanitization、ToolResultSanitization、可选 PII redaction | 用户文字、网页、工具输出不能伪装成框架权限 |
| 资源与范围 | ThreadData、Uploads、Sandbox、KnowledgeScope | 文件在哪里，这次允许使用哪一批资料 |
| 协议与模型边界 | DanglingToolCall、LLMErrorHandling、SystemMessageCoalescing | 历史工具消息成对，模型请求符合 provider 接口 |
| 动态上下文 | DynamicContext、SkillActivation、DurableContext | 加入日期、记忆、skill 和压缩后仍需保留的信息 |
| 上下文预算 | ToolOutputBudget、可选 Summarization | 大结果和长历史不会无限占据请求 |
| 模型可见能力 | MCP routing、DeferredToolFilter | 本轮该暴露哪些 schema |
| 输出与运行控制 | receipts、audit、subagent limit、loop、token budget、clarification | 模型回来以后如何执行或停止，下一站展开 |

这些处理按配置组合。例如 `memory_enabled=false` 会关闭该 agent 的记忆使用路径，日期上下文则独立保留。

## 顺序规则要按 hook 理解

~~~text
注册顺序：A, B, C

before_*：A → B → C
after_* ：C → B → A
wrap_*  ：A 包住 B，B 包住 C，返回时向外展开
~~~

这是 hook 自身的组合规律，不是说所有 middleware 都挂了所有 hook，也不是把 `wrap_tool_call` 当成 `after_model` 的普通逆序回调。工具包装围绕实际工具执行，模型包装围绕模型调用。

<SourceRef file="backend/packages/harness/deerflow/extensions/ordering.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="assert_ordering" /> 在 extension 组合完成后校验已声明的顺序约束。未纳入约束的依赖关系，需要结合 hook 实现与行为测试检查。

## before_agent：准备目录与执行资源

ThreadData 建立 thread 目录信息，Uploads 读取本轮上传上下文，Sandbox 管理执行资源。lazy 初始化通常将创建延迟到实际使用；受限 skill projection 与启用的 prewarm 则可能提前获取环境。

对于报告请求，上传完成只是有了文件；模型还需要知道文件的虚拟路径和用途。项目文档也可能通过索引与按需检索提供，不等于把整个项目全部塞入 prompt。

## before_model：把必须留下的信息从 messages 分离

<SourceRef file="backend/packages/harness/deerflow/agents/middlewares/durable_context_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="DurableContextMiddleware" /> 从消息中提取当前委派记录与已加载 skill，更新独立状态通道。<SourceRef file="backend/packages/harness/deerflow/agents/thread_state.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="ThreadState" /> 中还包括 `summary_text`、`tool_artifacts`、`task_notes` 等。

这些通道使“已经研究过什么、读过哪个 skill、得到什么产物”不必完全依赖一大段旧消息。委派按 run 与调用身份关联，不能把其他 run 中同名 provider tool-call ID 当作同一执行。

<SourceRef file="backend/packages/harness/deerflow/agents/middlewares/summarization_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 在启用且达到触发条件时压缩历史，保留继续执行所需的近期消息与协议边界。压缩不是把所有证据变成可靠结论：摘要、task notes 和子 agent 报告仍可能失真，需要通过原始来源重新核验。

## wrap_model_call：构造请求视图

这里必须区分两种写法：

| 操作 | 是否改变持久化图状态 |
| --- | --- |
| hook 返回 state update，经 reducer 合并 | 会改变图状态，是否耐久取决于 checkpointer |
| `request.override(messages=...)` | 构造本次模型请求视图，不自动改写 checkpoint |

<SourceRef file="backend/packages/harness/deerflow/agents/middlewares/dynamic_context_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 将变化频繁的日期和可用记忆放在动态上下文中，尽量保持基础 system prompt 稳定。<SourceRef file="backend/packages/harness/deerflow/agents/middlewares/durable_context_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="DurableContextMiddleware" /> 则临时加入权限说明与隐藏的数据消息，呈现摘要、委派、skills、产物和启用的任务连续性信息。

这些消息保留明确的权限层级：active goal 表达用户设定的目标，按用户请求处理；摘要、委派报告等历史字段按数据处理，不获得系统指令权限。

## 一处修补，可能影响多个 provider

<SourceRef file="backend/packages/harness/deerflow/agents/middlewares/dangling_tool_call_middleware.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 处理悬空 tool call。净化、压缩、故障回退和历史裁剪都可能改变消息，必须一起维护“调用与结果成对”的契约。

SystemMessageCoalescing 在请求边界合并 system 内容；ModelContentCompatibility 处理特定内容形式。它们解决的是发送给 provider 的请求兼容性，不意味着更改用户看到的历史记录。

<Philosophy>
把长期状态与短暂请求视图区分开，才能同时照顾恢复、上下文预算和 provider 协议。middleware 的价值不在数量，而在每一步都清楚自己的数据所有权：哪些事实要保存，哪些信息只应这次发给模型。
</Philosophy>

输入准备完成后，模型可以返回答案或提出工具调用。下一站继续跟随响应，看它如何经过裁决、执行和收尾。
