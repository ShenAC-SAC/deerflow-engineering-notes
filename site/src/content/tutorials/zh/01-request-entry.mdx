用户发出一句话：

> 请阅读项目资料，比较三种实现方案，生成一份带来源的 Markdown 报告。

接下来的九站都围绕这次请求：读取资料、按需委派研究、写出报告。**模型选择下一步动作，运行时负责提供能力、约束执行并保存结果。** 章节按理解流程所需的知识展开；实际执行中，skills 会参与装配，sandbox 可以延迟创建，子 agent 按需启动。

本章沿着前端到 Gateway 的路径，看一句文本怎样成为有身份、有生命周期、可观察的 run。

## 从输入框到 HTTP 请求

前端 <SourceRef file="frontend/src/core/threads/hooks.ts" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 使用 LangGraph SDK 的 `useStream`。发送路径先处理附件，再调用 `thread.submit()`：`messages` 装入文本与附件信息，`context` 带上模型、语言等运行选项，`threadId` 指定对话。

这条路径启用 `streamResumable`，没有开启 `streamSubgraphs`。子 agent 进度通过根命名空间的自定义事件到达；子图的完整 `values` 不能直接覆盖主线程状态。

反向代理将 `/api/langgraph/*` 转到 Gateway 的兼容路由。使用 LangGraph SDK 协议，**不等于后面必须运行官方 LangGraph Server**。

| 对象 | 本次请求中的职责 |
| --- | --- |
| thread | 容纳多轮对话及对应状态 |
| run | 在 thread 上进行的一次受托管执行 |
| LangGraph | 执行 agent 图和状态更新 |
| Gateway | 接入、权限、run、事件流、持久化与结束处理 |
| LangGraph Server | 可选宿主；不是本教程 Web 主链的中转站 |

## Gateway 从准入开始

<SourceRef file="backend/app/gateway/routers/thread_runs.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="stream_run" /> 检查创建权限和 thread 属主边界，再调用 <SourceRef file="backend/app/gateway/services.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="start_run" />。后者将客户端输入整理为符合身份、权限与协议约束的执行请求：

1. 规范化消息，剥离客户端伪造的服务端状态元数据与内部上下文键。
2. 注入认证身份，校验模型选择，并约束递归预算。
3. 固定本次项目资料范围；引用其他对话时准备只读访问能力。
4. 准备 graph input、配置和记录，交给 `RunManager.create_or_reject()` 做准入。
5. 创建成功后启动后台执行。幂等重试（客户端重发同一个请求）只复用已有记录，不会再执行一次。

项目上下文是在入口确定的服务端快照。对示例而言，它回答“项目资料指哪一批文件”，避免同一次 run 因中途修改项目关系而获得两套上下文。

<MarginNote>checkpoint 是 LangGraph 在图的每一步之后保存的状态快照，后面恢复对话、继续执行都靠它。下一节表格里“可由图更新和 checkpoint 的数据”，指的就是会被这样保存的部分。</MarginNote>

<MarginNote>消息里写“我是管理员”只是一段文字。thread、模型和工具权限来自认证与授权链，不能由这句话授予。</MarginNote>

## config、context 和状态分别装什么

<SourceRef file="backend/app/gateway/services.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="build_run_config" /> 将请求翻译成 LangGraph 配置。`configurable` 与 `context` 承载不同调用方需要的运行选项；入口按规则映射字段，并过滤客户端提供的内部键。

| 载体 | 典型内容 | 应怎样理解 |
| --- | --- | --- |
| RunnableConfig | thread/checkpoint 定位、递归限制、callbacks | 图调用配置 |
| Runtime.context | run、用户、AppConfig、宿主能力 | 当前执行环境 |
| ThreadState | messages、summary、skills、delegations、artifacts 等 | 可由图更新和 checkpoint 的数据 |
| RunRecord | 状态、归属、取消意图、完成信息 | 图外部的生命周期 |

<SourceRef file="backend/packages/harness/deerflow/runtime/runs/worker.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="run_agent" /> 组装 `Runtime(context=..., store=...)` 并接入图调用。宿主能力对象和密钥属于执行期上下文，需要与可持久化的状态和 metadata 分开。

## 同一条执行链，三种等待方式

后台创建立即返回记录；`/runs/stream` 返回 SSE（Server-Sent Events，服务端单向推送的事件流）；`/runs/wait` 等待完成。它们共享启动与生命周期逻辑。

`StreamBridge` 分开事件生产与 HTTP 消费。断连后，`on_disconnect=continue` 允许后台继续，`cancel` 请求取消；后者仍须遵守所有权与收尾协议。重新加入已有 run 的观察流，不等同于创建 run，也不会照搬创建端的断连取消策略。

响应中的 `Content-Location` 让 SDK 得到规范的 run URL。内存 bridge 只服务当前进程：别的 worker 上有持久化记录，不代表本机有实时流。这类不支持的订阅会被路由直接拒绝，而不是让客户端空等一条永远不会有事件的流。

## 模型开始前，run 已有生命周期

<SourceRef file="backend/packages/harness/deerflow/runtime/runs/manager.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="RunManager" /> 负责准入、状态、归属与取消；<SourceRef file="backend/packages/harness/deerflow/runtime/runs/worker.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="run_agent" /> 调用图、发布事件并完成收尾。它们都不是模型本身。

启用 heartbeat 的多 worker 部署可以持久化远端取消意图，由属主观察后执行；租约过期的回收也要检查所有权。单进程配置有不同边界，第九站再展开。

<Philosophy>
Gateway 把模型交互变成可管理的应用运行。代价是维护 SDK 协议、图状态与业务记录之间的适配。读入口时，先认清谁接受请求、谁拥有执行、谁发布结果、谁有权结束它。
</Philosophy>
