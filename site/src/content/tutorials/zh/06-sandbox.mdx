假设模型已经决定读取项目文件，再写出报告。工具 schema 告诉模型如何调用，sandbox 则回答：**在哪执行，文件属于谁，执行结束后资源怎么办？**

Sandbox 提供统一操作接口，具体隔离能力取决于执行环境。Local、容器与远端服务的边界不同；阅读实现时，需要分别检查路径、命令、网络与操作系统隔离。

## 会话身份、资源句柄与归属检查

`thread_id` 是产品会话身份，`sandbox_id` 是资源句柄。<SourceRef file="backend/packages/harness/deerflow/sandbox/sandbox_provider.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="SandboxProvider.get_scoped" /> 按 thread 和 user 查找资源。默认实现在无法证明归属时返回空；调用方随后走规范的 acquire 路径取得资源。

恢复长期会话时，checkpoint 中的资源记录可能仍在，但对应进程、容器或客户端可能已经退出。因此复用前需要确认资源存在且归属匹配。

## Local 与隔离 provider 的区别

<SourceRef file="backend/packages/harness/deerflow/sandbox/local/local_sandbox.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" symbol="LocalSandbox" /> 主要在宿主环境中适配文件与命令。host bash 需要显式放行，相关准入在 <SourceRef file="backend/packages/harness/deerflow/sandbox/security.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 与工具装配层。虚拟路径只能约束经过该路径处理的操作，不能让任意宿主 shell 自动进入容器。

AIO 通过容器或远端 provisioner 提供执行环境；E2B 等 provider 通过服务接口获得资源。当前社区目录也有 BoxLite、OpenSandbox、Tenki 等实现。不同实现的创建、容量、挂载、网络和回收语义应分别阅读，不能从统一类名推断等价保证。

| 问题 | 应检查的地方 |
| --- | --- |
| 文件操作能到哪里 | 工具的路径解析与 provider 文件系统 |
| shell 能到哪里 | host bash gating 与实际执行环境 |
| 网络允许访问哪里 | provider 支持的网络策略与配置 |
| 并发多少环境 | provider 容量机制及部署配置 |
| 用户之间如何隔离 | 身份解析、资源归属、挂载与服务端授权 |

## 给模型稳定路径，给宿主真实路径

模型通常看到 `/mnt/user-data/workspace`、`uploads`、`outputs` 等虚拟目录。Local 可以将它们映射到宿主目录，挂载型 provider 可以映射成容器路径，远端 provider 可能需要上传或下载。

因此，报告写在虚拟路径上，不等于宿主的同名绝对路径存在。<SourceRef file="backend/packages/harness/deerflow/sandbox/tools.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 将工具调用连接到 sandbox，并处理输出元数据；下载和产物展示还要走对应文件服务。

`/mnt/skills` 也不是随便把整个技能库挂进去。<SourceRef file="backend/packages/harness/deerflow/skills/projection.py" sha="51d59a1cdff92626bd9f03f1b2254f34a824ca3e" /> 构建启用状态与允许范围对应的文件视图，技能系统一站会解释它与 skill 授权的关系。

## 延迟获取与共享执行租约

SandboxMiddleware 默认延迟获取资源；没有受限技能投影或预热需求时，只回答文字可以避免创建远端环境。受限 agent 的技能投影可能在 before_agent 就要求 acquire，同步文件视图；启用的 prewarm 也可以提前准备环境。真正开始使用后，lead 与 subagent 各自持有 execution lease。

它解决的具体问题是：lead 完成自己的工作时，子 agent 可能还在读文件；一个 execution 的 release 不能让仍工作的子 agent 丢失环境。最后一个借用者才触发 provider release，远端 provider 可以将资源停放在 warm pool。

**这里的 lease 是进程内资源借用管理。** 它与 RunManager 的 worker 所有权租约不是同一机制，也不能单独证明跨进程协调。AIO ownership、E2B 容量等还有各自的实现与配置。

## 技能视图也有资源所有权

lead 可以为自己的 agent policy 构建 thread skill projection。子 agent 共享 thread sandbox，因此不能按自己的 skill 列表重建整份共享挂载，否则会改变其他并发执行正在使用的文件。

provider 通过 `supports_agent_skill_isolation` 声明是否能实际执行这个边界。不支持时，受限 agent 的物理技能隔离不能默默降级成“提示词里少列几个名字”。

## 取消时的资源清理

正常 `after_agent` 会释放占用；异常和取消路径也需要 worker、工具与生命周期 helper 配合。一个同步 provider 操作即使调用方被取消，也可能还在后台线程运行，因此不能在实际操作未结束时就提前撤掉它依赖的资源。

<Philosophy>
sandbox 生命周期首先是资源所有权问题，然后才是“何时销毁”。保留 thread 数据、复用预热环境和释放本次借用是三件不同的事。把它们分开，才不会用一次聊天结束误删另一段仍在执行的工作。
</Philosophy>
